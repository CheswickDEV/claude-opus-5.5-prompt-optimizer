# Opus 5.5 Prompting Rules (R1–R54)

Every rule carries an evidence marker:

- **[DOCUMENTED: source]** — stated in official Anthropic sources.
- **[DERIVED]** — a hypothesis inferred from documented properties, not a fact.
- **[DOCUMENTED: PromptO5] + [DERIVED: transfer]** — measured by Anthropic on Claude Opus 5; [PromptO55] says the Opus 5 patterns "remain a reasonable starting point" and [Migration] says Opus-5-tuned instructions "may no longer be needed". The optimizer applies these only when the prompt shows the matching symptom or gap, and flags them as re-test candidates.
- **[MEASURED: …]** — this project's own measurement on Opus 5.5 (T3/T5: blind pairwise eval judged by Claude Fable 5.1; T1: behavior checks of the optimizer's own output; October 2026; method and limits in the README section "Evaluation"). It is evidence from a small test set, not an Anthropic statement, and it ranks below [DOCUMENTED] where the two disagree on facts about the model.
- *[generic]* — per [BestPract], the technique applies to all current models including Opus 5.5 ("Where a technique names a specific model, treat it as measured on that model and re-check it against your own evals before applying it to another").

**Goal hierarchy (applies to every rule and recommendation):** the best outcome comes first; token and cost efficiency come second. A cheaper setting or a shorter prompt is recommended only where the sources show no quality loss; savings are reported as a secondary benefit, never traded against quality.

Source codes resolve to URLs in the legend of `01-opus55-model-facts.md` and at the bottom of this file. When the optimizer logs a change, it cites the rule number(s) that motivated it.

## Group A — Structure & Explicitness

**R1 — Instruct clearly, explicitly, completely.** Golden rule: if a colleague with minimal context would be confused by the prompt, so is Claude. Be specific about output format and constraints; use numbered lists when order or completeness matters; request "above and beyond" behavior explicitly instead of hoping the model infers it. *[generic]* **[DOCUMENTED: BestPract]** — Explicit means stating what the user wants, not adding requirements they never stated: for human readers, sections, tables, columns, citation duties, or "open questions"/"inferences" sections the user did not ask for made Opus 5.5's answers longer and buried what mattered, while correctness stayed the same; for parsers, a fixed schema clearly helped. The same holds for an agent's final report: rewrites that added reporting duties the user did not ask for ("say which kinds and formats you compared and how, and name anything you couldn't check"; "the judgment calls you made where the ticket left a choice open") came with final reports 26–47% longer than with the user's own prompt (an interactive refactor; a ticket agent run unattended), while every hidden test passed; the judge preferred the original in 2 of 3 comparisons each (1 tie), citing the overlong summary or the added decisions section, and in the refactor also weaker code structure. The rewrites changed more than the report duties (one without such a duty was also 39% longer), so this is an association, not an isolated effect. Missing format or length → ask in `<open_questions>`. Keep the user's scope words: a general statement ("the config lives in `config/<env>.toml`") does not become an explicit "for every existing environment" — in one measured unattended task the widened wording made the agent create a copy that shadowed a production file the repository marks as owned by another team (3 of 3 runs); with the user's own wording, and with the optimizer's prompt after this rule, in 0 of 3. **[MEASURED: T3 eval, October 2026]**

**R2 — Provide context and motivation.** Explaining why an instruction matters lets the model generalize from the explanation ("Your response will be read aloud by a text-to-speech engine, so never use ellipses…" beats "NEVER use ellipses"). Purpose, audience, and what the output enables belong in the prompt. *[generic]* **[DOCUMENTED: BestPract]** — Context the user did not give goes into `<open_questions>`, never into the prompt as a `[bracketed]` gap or an invented example: used as pasted, such gaps made the answers worse than the original prompt's (meta comments about the gap, answers steered toward the invented example), while the answered version beat the original. **[MEASURED: T3 eval, October 2026]**

**R3 — XML tags to structure** complex prompts that mix instructions, context, examples, and variable inputs; consistent, descriptive names; nest natural hierarchies. *[generic]* **[DOCUMENTED: BestPract]**

**R4 — Long inputs (20k+ tokens) at the top, query at the end** ("can improve response quality by up to 30 percent"); multiple documents in `<documents>` / `<document index="n">` with `<source>` and `<document_content>`; for long-document tasks, have the model extract relevant quotes first. No Opus-5.5-specific placement rule is documented. *[generic]* **[DOCUMENTED: BestPract]**

**R5 — Examples: 3–5 relevant, diverse examples in `<example>`/`<examples>` tags** are one of the most reliable ways to steer format, tone, and structure. *[generic]* **[DOCUMENTED: BestPract]** — For communication style, the Opus 5 guide adds: "Positive examples of the communication style you want tend to be more effective than instructions about what not to do." **[DOCUMENTED: PromptO5] + [DERIVED: transfer]**

**R6 — Set a role in the system prompt** — even a single sentence focuses behavior and tone. Where the deployment needs model self-knowledge, the documented identity line is "The assistant is Claude, created by Anthropic. The current model is Claude Opus 5.5." *[generic]* **[DOCUMENTED: BestPract]**

**R7 — Mark text the user pasted from elsewhere.** Wrap each pasted block (emails, web pages, tickets, transcripts) in `<pasted_content id="…">` … `</pasted_content id="…">` with the same short random ID, each tag on its own line, and add the documented system-prompt note (snippet 14). Opus 5.5 is robust against injected instructions in pasted content only "with the right context". **[DOCUMENTED: PromptO55]** — Background: the System Card lists being "more likely to follow malicious instructions planted in text a user pastes into their own prompt" as a regression; the model "often reasoned that anything in the user's message must come from the user". Injection via tool results: 0 of 105. **[DOCUMENTED: SystemCard]** — Caveats: the tags can be imitated (one guardrail among several), and the note "can make the model slightly more cautious at times". **[DOCUMENTED: PromptO55]** — Placement: the documented setup is an application that generates the ID and puts the note in its system prompt. For a claude.ai Project, put the note in the Project instructions; for a single pasted chat prompt, put it at the top of the prompt. Both are adaptations, and in a hand-typed chat prompt the note's "the user never sees the id" clause is not literally true. **[DERIVED]**

**R8 — Multi-app workflows: explore before acting.** Opus 5.5 "tends to get to work quickly"; on loosely specified tasks across email, documents, spreadsheets, and records, one sentence makes it look through sources the request didn't name before changing anything (snippet 22). Measured: noticeably more tasks completed correctly at `medium` and `max`, slightly more tool calls. Keep untrusted content out of the searched records, because the instruction tells the model to act on what it finds. **[DOCUMENTED: PromptO55]**

## Group B — Thinking & Effort Signals in the Prompt

**R9 — Never ask the model to reproduce its reasoning in the output.** Prompts that push it to write out its thinking may be declined with `stop_reason: "refusal"`, category `reasoning_extraction`. Documented triggers: a `<thinking>`, `<reasoning>`, or scratchpad section the model fills in before answering; a `reasoning`, `thinking`, or `trace` field in JSON output or a tool input; the model's "private notes" or a running reasoning log; reasoning "verbatim or in full". The wording can sit in a system prompt, a skill, a tool description, or a schema. This category is billed before any output, has no recommended fallback model, and is not retried by server-side fallback — "change the prompt rather than retry". Allowed instead: a short explanation of the answer, the evidence behind a result, a summary of the actions taken; for reasoning visibility, `display: "summarized"` (API). **[DOCUMENTED: PromptO55, PromptO5, Refusals, StructOut]**

**R10 — Do not configure thinking off or budgeted.** Thinking is always on; `thinking: {"type":"disabled"}` and `{"type":"enabled","budget_tokens":N}` return 400 at every effort level. Omit `thinking` (or send `adaptive`) and steer depth with `effort`. **[DOCUMENTED: WhatsNew, ModelPage, Effort, Migration]**

**R11 — Lower effort before prompting for less thinking.** "To get less thinking, lower the effort level first. Lowering effort reduces thinking, and with it cost and latency, more reliably than prompt instructions do." Only where time-to-first-token still matters after that, the documented line "Answer directly without deliberating." may be added — measure quality, because less thinking can lower it. **[DOCUMENTED: PromptO55, ThinkSteer]**

**R12 — Remove "think carefully" lines in chat prompts and manual chain-of-thought everywhere.** *Chat:* "In chat applications, if your system prompt contains instructions that tell Claude to think carefully before answering, consider removing them for Claude Opus 5.5"; removing such a line "made replies start sooner, with no clear decline in the quality of the reply". **[DOCUMENTED: PromptO55]** *All routes:* manual CoT ("think step by step", hand-written step-by-step reasoning plans) is the thinking-off fallback — on Opus 5.5 "rely on thinking instead, at a lower effort"; a general instruction like "think thoroughly" "often produces better reasoning than a hand-written step-by-step plan". **[DOCUMENTED: BestPract]** Outside chat, a targeted encouraging line remains legitimate where effort must stay low for a genuinely multistep task ("This task involves multistep reasoning. Think carefully before responding."), and the per-message phrase "Please think hard before responding." serves a single hard turn. **[DOCUMENTED: ThinkSteer]**

**R13 — Remove relics of thinking-disabled integrations.** Delete every rule telling the model not to think or reason ("remove the no-thinking rule either way"). Re-test the Opus 5 thinking-off mitigation ("When you use a tool, you may say a brief sentence first…") — it addressed artifacts that appear only with thinking disabled — "check whether you still need the instruction". Reasoning-in-the-response substitutes fall under R9. **[DOCUMENTED: PromptO55, PromptO5]**

**R14 — Multi-turn chat: settle earlier answers (opt-in).** Opus 5.5 "sometimes goes back over an earlier answer while it thinks about a new message", which adds thinking and latency. Where earlier answers should count as settled, add the two documented sentences at the end of the system prompt (snippet 9). Leave them out of long analyses and agentic tasks where a later step can reveal an earlier mistake; the instruction may make the model less likely to point out an earlier mistake on its own. **[DOCUMENTED: PromptO55]** — Quality-first: insert only when the user states that reply latency matters, because of that documented risk. **[DERIVED: quality-first policy]**

## Group C — Verbosity, Communication & Format

**R15 — Steer response length explicitly; effort is not the length lever.** "The effort parameter controls how much the model thinks rather than how much it says." For user-facing multi-turn products, a short conciseness instruction (snippet 1) works; in a long system prompt, pair it with a `<tone_preference>` reminder near the end (snippet 2). **[DOCUMENTED: PromptO5] + [DERIVED: transfer]** — Opus 5.5 itself writes more tightly than Opus 5 ("puts the most important information up front"; tester: "40% less verbose without losing accuracy" [News]), so insert the snippet only when the prompt has no length steering for a user-facing answer (a chat prompt or a user-facing product), not into deliverables (R16) or prompts that already steer length. Measured on Opus 5.5: on two chat answers without length steering, the version with snippet 1 won all 6 blind comparisons and used 29–41% fewer output tokens. **[MEASURED: T5 ablation, October 2026]**

**R16 — Calibrate the length of written deliverables.** Files the model writes (reports, Markdown documents, summaries) ran long on Opus 5; when the product ships model-authored documents, add the deliverable-length line (snippet 3). **[DOCUMENTED: PromptO5] + [DERIVED: transfer]**

**R17 — Describe the communication cadence, not just the amount.** For agentic sessions with a human reader: a one-sentence statement of intent before the first tool call, brief updates only on important findings or changes of direction, outcome first at the end (snippet 4). The lever is documented for Opus 5.5 — "say so in the system prompt; the model is responsive to such instructions", "This helps most in human-in-the-loop work" **[DOCUMENTED: PromptO55]**; the snippet wording was written for Opus 5, to tune its narration *down* **[DOCUMENTED: PromptO5] + [DERIVED: transfer]**.

**R18 — Limit correction narration.** For user-facing products, only correct an earlier statement when the error would change the user's code, conclusions, or decisions (snippet 5). **[DOCUMENTED: PromptO5] + [DERIVED: transfer]**

**R19 — Steer format positively and by example.** Tell the model what to do instead of what not to do ("flowing prose paragraphs" beats "no markdown"); prompt style influences output style. Opus 5.5's own claude.ai prompt shows its defaults: minimal formatting for clarity, a direct answer to a simple question. Prefill-era preamble suppression becomes a system-prompt line (snippet 18). *[generic]* **[DOCUMENTED: BestPract, SysPrompt]**

**R20 — Frontend design: name the specific patterns to avoid.** Without design direction Opus 5.5 "falls back on a few default styles, and a general instruction such as 'avoid a generic AI look' mostly swaps one default for another. It responds well to instructions that name specific patterns to avoid." Work iteratively: check which styles the first result used, extend the list (snippet 23). This is the documented exception to R19's positive-phrasing rule, and it supersedes the generic `frontend_aesthetics` sample in [BestPract] for this model. **[DOCUMENTED: PromptO55]**

## Group D — Agentics, Autonomy & Harness Behavior

**R21 — Scope discipline for narrow tasks.** Deliver what was asked at the intended scope, make routine judgment calls, check in only when readings diverge materially, say so in a sentence if the request seems mistaken and continue as asked, finish the whole task (snippet 6). **[DOCUMENTED: PromptO5] + [DERIVED: transfer]**

**R22 — Verification: keep the user's own lines, add no blanket ones, drop verifier subagents.** On Opus 5, which "verifies its own work without being told to", instructions like "include a final verification step for any non-trivial task", "use a subagent to verify", "double-check your answer", "re-verify before responding" cause over-verification; "removing them reduces wasted tokens with no loss in quality". **[DOCUMENTED: PromptO5]** For Opus 5.5 this is a transfer, and a contested one: the generic guidance that covers Opus 5.5 still recommends "Ask Claude to self-check … 'Before you finish, verify your answer against [test criteria].' This catches errors reliably" and names only Opus 5 as the exception ([BestPract]). **[DERIVED: transfer]** Measured on Opus 5.5: adding a typical blanket line ("double-check your work and re-verify every change and claim; include a final verification step") to the optimized prompt never changed the objective checks or tests — of 9 blind comparisons across a long-document analysis, a bug fix, and an unattended feature task, 3 favored keeping it, 1 favored removing it, 5 were ties; token cost ranged from −1% to +41%. **[MEASURED: T5 ablation, October 2026]** → Quality-first policy: the optimizer keeps a verification instruction the user wrote (tightening it into a check against concrete criteria — tests, a spec, a build — where the task has them), adds no new blanket verification, and removes verifier *subagents* (R46). Dropping a blanket line to save tokens is offered only on request. Distinct from R29: grounding *claims* in evidence always stays.

**R23 — Cap subagent delegation.** The Opus 5 line delegates "more readily than prior models"; give explicit guidance on when delegation is warranted, or set deterministic caps (snippet 7; Claude Code/Agent SDK: `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, `max_budget_usd`). **[DOCUMENTED: PromptO5] + [DERIVED: transfer]** — Opus 5.5 does run long audits and migrations "end to end with parallel subagents" well ([PromptO55]); the cap targets small tasks, not genuinely parallel tracks. Measured on Opus 5.5: with the Agent tool available, it spawned no subagent in any of 12 runs on two unattended multi-step coding tasks — 6 without delegation guidance, 6 with snippet 7 — so the cap neither helped nor hurt there. Insert it when the prompt pushes delegation or the harness is built around subagents, not by default. **[MEASURED: T5 ablation, October 2026]**

**R24 — Boundaries proportional to the risk, without over-scaffolding.** For prompts that grant access to state (repos, files, accounts, shared systems): local, reversible actions are fine; ask before hard-to-reverse, shared, or destructive actions (snippet 17). The snippet was introduced for Opus 4.6 ("If you want Claude Opus 4.6 to confirm before taking potentially risky actions") in the all-models section of the guide. **[DOCUMENTED: BestPract] + [DERIVED: transfer]** — Opus 5.5 "took overeager or destructive actions less than any other model we tested" and is "more likely to ask the user for permission before proceeding with a potentially destructive action" ([SystemCard]); a short paragraph naming the deployment's actual risky actions is therefore probably enough, and long generic enumerations add little. **[DERIVED]** The optimizer applies the same standard to itself: it never writes a destructive step (delete files, drop a fallback, migrate data) into a prompt unless the user asked for it. **[MEASURED: T3 eval, October 2026]** — Agents whose tools act outside the session (post comments, send messages, approve or merge, deploy) always get such a paragraph, also when they run unattended, and such an agent is Route L or XL (03) **[DERIVED]**; the snippet lists "Operations visible to others: pushing code, commenting on PRs/issues, sending messages" among the "actions that warrant confirmation" **[DOCUMENTED: BestPract]**. Name the outside-effect actions the task pre-approves (R26); any other one waits for confirmation or, where nobody can confirm, is reported instead of taken **[DERIVED]**. A CI review bot whose tool posts comments got no such paragraph in the call-matrix test (case 9, skill and Project variants); after this rule, both did. **[MEASURED: T1, October 2026]**

**R25 — Unattended runs: keep the agent running without false "done".** Some progress updates end the turn with text (`stop_reason: "end_turn"`); an unattended loop that treats that as completion stops early. Documented harness + prompt pattern: keep the task's parts in a checklist the model updates; if a turn ends with open items and no stated blocker, send a short continuation message (snippet 11); optionally let a smaller model check a stated completion condition; stop after two or three automatic continuations; wait for running background work before declaring done. For fully unattended agents, add the standing instruction (snippet 10) at the **end** of the system prompt **from the first request** (adding it later invalidates earlier thinking blocks). Leave it out of human-in-the-loop apps. **[DOCUMENTED: PromptO55]**

**R26 — Keep explicit confirmation for risky actions under "act, don't ask".** The standing instruction itself says it "does not override the need for confirmation on risky or destructive actions", and [PromptO55] tells harnesses to keep their own confirmation step. **[DOCUMENTED: PromptO55]** — The System Card documents rare (<0.01%) "overclaiming user intent", including a fabricated user approval under an act-don't-ask instruction, and "more often accepting unverifiable claims of authorization" ([SystemCard]). An optimizer should therefore never write "you have full permission/authorization" boilerplate, and should state concretely which actions are pre-approved. **[DERIVED]**

**R27 — Progress updates: four levers.** (1) API: set `thinking.display: "updates"` (beta `thinking-display-updates-2026-08-18`), otherwise between-tool notes arrive as empty `thinking` blocks and the client looks silent. (2) For verbatim mid-turn content, a simple send-message tool reserved for that content, declared in `tools` from the first request. (3) For predictable cadence, say so in the system prompt (R17). (4) If turns still go quiet, the harness appends the silence reminder (snippet 13) as a turn-scoped system message after ~5 silent tool steps, at most 2–3 times; measured: "roughly halved the share of tasks with a long silent stretch". **[DOCUMENTED: PromptO55, WhatsNew]**

**R28 — Remove forced interim-status scaffolding and update suppressors.** "If you've added scaffolding to force interim status messages ('After every 3 tool calls, summarize progress'), try removing it." — stated in the Opus 5.5 migration guide's section on behavior changes inherited from Opus 4.7 ("Claude Opus 4.7 provides more regular, higher-quality updates"), and applied there to Opus 5.5. **[DOCUMENTED: Migration]** — Suppressors written for chatty models ("don't narrate", "hold all findings for the final message") compound the silent-client effect of R27, because updates already come back hidden by default; remove them and use R17 for the cadence you want. **[DERIVED]**

**R29 — Ground claims in evidence and label inferences.** The System Card's top flagged internal-use behavior was "asserting unverified inferences as established fact", followed by "dismissing its own doubts or abandoning its own stated plan"; examples include "describing a partial check as a full read". **[DOCUMENTED: SystemCard]** → For status-reporting agents — unattended runs whose report is read by someone who did not watch the work — instruct that every reported claim points to a tool result from the session and that unverified conclusions are labeled as such (snippet 19). **[DERIVED]** This is claim hygiene, not an extra verification pass (R22). Scope: status reports of unattended runs and outputs the user needs sourced (audits, compliance, investigations); not the final summary of an interactive session unless the user asks for sourcing; in ordinary human-facing analyses, inference labels and citation duties the user did not ask for added clutter without improving correctness. **[MEASURED: T3 eval, October 2026]** Security triage of a pasted e-mail or log for the person who acts on it (an analyst, an admin) counts as such an analysis, not as an investigation report: in an analysis that ends in a verdict, one sentence that bases the verdict on what the input shows and names what the input cannot settle (a domain's age, whether a request succeeded elsewhere) as a check to run is enough; per-indicator or per-line citations only when the user asks. **[DERIVED]** On a log triage, a rewrite that required citing the log lines behind each conclusion, together with a fixed four-part answer and bracketed context gaps, lost all 3 blind comparisons to the original (one to a safety-classifier cut-off; in the other two correctness was equal and the judge faulted length, meta comments about the gaps and a gaps table). Rewrites that kept the user's three questions and added one grounding sentence (plus the pasted-content wrapper and the conciseness snippet) did not beat the original either but stayed close — 0–1–2 before and 1–2–0 after the user's answers, at equal correctness, with mostly low-confidence verdicts. **[MEASURED: T3 eval, October 2026]** A review's findings are not a status report: an unattended review bot gets snippet 19 at most for its run summary, no per-finding evidence duties (R32). **[DERIVED]**

**R30 — Time signals for multi-agent harnesses.** Opus 5.5 "pays close attention to information about elapsed time". If a sensible duration is known, the harness appends `elapsed 340s / 1200s`-style lines (set the budget above the time you want; the model usually finishes well before it). Otherwise show elapsed time alone and add the time-matters sentence (snippet 12). The budget is advisory — keep a hard timeout; under time pressure the model may search and verify a little less. **[DOCUMENTED: PromptO55]** — Quality-first: use time signals only when finishing sooner is a stated goal, and check answer quality when you do. **[DERIVED: quality-first policy]**

**R31 — Long-horizon state lives outside the context.** Structured state files (JSON), free-text progress notes, git as a log, tests/setup established early; design state artifacts so a new session recovers context fast. *[generic]* **[DOCUMENTED: BestPract, ContextWin]** — If the harness compacts, say so (snippet 20, first sentence). The full snippet sits in the guide's context-awareness section and talks about the model's "token budget", which Opus 5.5 does not see (no injected budget tags, [ContextWin]); hence only the compaction sentence is carried over. **[DOCUMENTED: BestPract] + [DERIVED: transfer]**

**R32 — Code review: report everything, filter separately.** "If your review prompt says 'only report high-severity issues' or 'be conservative,' the model may follow that instruction literally and report less; ask it to report everything and filter in a separate pass instead." **[DOCUMENTED: PromptO5] + [DERIVED: transfer]** — Opus 5.5 code review catches more bugs with fewer false alarms than Opus 5 ([PromptO55]). The rule removes a severity filter the prompt contains; it does not add "report every issue, even minor ones" to a review prompt that has no filter: for a review a person reads, a rewritten prompt that added this line, together with per-point evidence labels and a fixed answer structure, produced reviews about twice as long that buried the critical findings. **[MEASURED: T3 eval, October 2026]**

## Group E — Parameter Recommendations (for the optimizer's output)

**R33 — Set `effort` explicitly, for the best result.** Facts: the default is `medium` (on every other model that supports effort it is `high`); level names do not mean the same amount of thinking across models; at a given level Opus 5.5 thinks more than Opus 5. Anthropic's documented starting point is `medium` with a sweep of neighboring levels, reserving `xhigh`/`max` for "work where you've measured a quality gain". Measured accuracy on SWE-bench Pro, relative to `high`: `medium` ≈ −2.5 points, `low` ≈ −8, `xhigh` ≈ +1.4 ("Long-horizon coding is where effort genuinely buys accuracy"); on knowledge work, `medium` already matches or beats Opus 5 at `high`. **[DOCUMENTED: Effort, PromptO55, CostIntel]** → Optimizer policy (best outcome first): coding, agentic, and long-horizon work → `high`; the hardest or correctness-critical work → `xhigh` (an explicitly set `xhigh`/`max` is kept, with its token cost noted); knowledge work → `medium`, `high` for critical deliverables; `low` only for simple tasks and subagents where quality holds. Token savings are offered as a secondary option, never as the default — e.g. `low` with failures re-run at `high` (~97% vs. 95.3% all-`high`, at ~$0.17 vs. $0.29 — roughly 60% of the cost per task). Per-message effort (beta) varies effort per turn without a cache reset. **[DERIVED: quality-first policy]** — `low` as the start for chat, classification, and extraction is documented for the Sonnet line, not for Opus 5.5. **[DERIVED: transfer]** Measured on Opus 5.5: `low` held the quality of a short chat explanation, but on a JSON classifier without structured outputs it broke the output format in 3 of 3 runs, where `medium` stayed valid. `xhigh` vs `high` on a bug fix and an unattended feature task: 2 wins each, 2 ties, at 1.6–2.2× the tokens — no measured quality gain there. Use `low` only where quality holds and the format is enforced by `output_config.format`. **[MEASURED: T5 ablation, October 2026]**

**R34 — Size `max_tokens` for thinking plus the reply.** Thinking counts toward `max_tokens` even when its text isn't returned. Long agentic coding turns: 128,000 "has worked well in Anthropic's testing" (requires streaming); at `xhigh`/`max` start at no less than 64k. `max_tokens` is invisible to the model, so lowering it does not make the model economize — a 16,384-token cap ended about a quarter of Opus 5.5's attempts on an internal repository benchmark. **[DOCUMENTED: PromptO55, Migration, CostIntel]**

**R35 — Omit sampling parameters.** Non-default `temperature`/`top_p`/`top_k` → 400 on every request (the Python SDK raises a `TypeError` before sending); "Use prompting to guide the model's behavior." Determinism substitute: tighter prompt plus structured outputs; variance substitute: an explicit variance instruction. **[DOCUMENTED: Migration, Thinking]** (substitutes: **[DERIVED]**)

**R36 — No assistant prefill.** A prefilled last assistant turn → 400. Format control via structured outputs; preamble control via the system-prompt line (snippet 18); classification via a tool enum or structured outputs. **[DOCUMENTED: Migration, BestPract]**

**R37 — No forced tool use.** `tool_choice` `any`/`tool` → 400 (also on the token-counting endpoint). Use `auto` and say in the prompt when the tool applies; add `strict: true` for schema-valid arguments (every object in the schema sets `additionalProperties: false`; per request at most 20 strict tools, 24 optional and 16 union-typed parameters across all strict schemas); when the forced call existed only to get JSON back, use structured outputs. **[DOCUMENTED: WhatsNew, Migration, StructOut]** — Because `auto` does not guarantee a call, the harness should check that one happened and retry if not. **[DERIVED]**

**R38 — Structured outputs for machine-readable results.** `output_config.format` (`{"type": "json_schema", "schema": …}`; every object sets `additionalProperties: false`; never the deprecated top-level `output_format`, which returns 400 without its old beta header) or `strict: true` tools; never include a property that asks for the model's thinking or step-by-step reasoning (R9) — "Ask for a short explanation instead"; incompatible with citations (400). **[DOCUMENTED: StructOut]**

**R39 — Refusal handling and domain check.** Branch on `stop_reason: "refusal"` (HTTP 200) before reading `content`; treat `stop_details` as informational; discard partial output on a mid-stream refusal. Opt into server-side `fallbacks: "default"` (beta `server-side-fallback-2026-07-01` on the Claude API; not available on Bedrock, Google Cloud, or Foundry; routes by category), the SDK middleware or an own retry on other platforms, and resubmission of refused items for Message Batches (no `fallbacks` parameter, no fallback credit there). Domain check: finding vulnerabilities in source code is allowed; the cyber, biology, and distillation safeguards "all … fall back to another model transparently" — "most cybersecurity tasks will be re-routed to Opus 4.8", and in Anthropic's runs biology and frontier-LLM-development tasks were completed by Opus 5; without a fallback configured, such requests end as refusals. Life sciences organizations can apply to the Life Sciences Verification Program. A fallback model runs without Opus 5.5's thinking. **[DOCUMENTED: Refusals, PromptO55, News, WhatsNew]**

**R40 — Choose `thinking.display` deliberately.** Default `"omitted"`; `"updates"` (beta) for user-facing agent UIs; `"summarized"` when reasoning visibility is needed (the R9 alternative). Read content blocks by `type`; pass thinking blocks back unchanged. **[DOCUMENTED: Thinking, WhatsNew, PromptO55]**

**R41 — Plan for prompt caching.** Stable prefix (tools → system → messages, byte-exact); minimum 512 tokens; cache reads cost 0.05× input (most models: 0.1×; Fable 5.1/Mythos 5.1: 0.025×), so a miss costs relatively more than on most models. Changing top-level `effort`, the thinking config, or the system prompt between requests invalidates the cache — use per-message effort and mid-conversation system messages instead. With short pauses (a turn or two in 20 pausing up to ~30 min), keep the 5-minute cache warm instead of buying the 1-hour duration. **[DOCUMENTED: ModelPage, Pricing, CostIntel, MidConvSys]**

**R42 — Preserved-thinking-compatible harness.** Keep history append-only: change instructions with mid-conversation `role: "system"` messages, add tools via `tool_addition` or declare every tool the session may need (including a send-message tool) from the first request, append per-turn reminders and leave them in place, and put standing instructions in the system prompt from request one. Accounts created on/after 2026-08-31 get a 400 when a replayed block's prefix changed; `drop_block` (beta `thinking-binding-controls-2026-08-01`) drops instead. Compaction: server-side or on-demand (beta `compact-2026-09-04`, custom `instructions`; the compaction request itself must omit `context_management`, `stop_sequences`, a forced `tool_choice`, a structured-output `output_config.format`, and `task_budget.remaining` — the latter also on every later request that carries the compaction block); `role:"system"` messages inside a summarized range must be restated. **[DOCUMENTED: WhatsNew, PreservedThinking, MidConvSys, CompactOnDemand, PromptO55, BestPract]**

**R43 — Task budgets only with a measured value.** The only model-visible countdown on Opus 5.5 (no context-awareness tags); beta `task-budgets-2026-03-13`, minimum 20,000; advisory, `max_tokens` stays the hard cap; "A budget that is too small for the task can cause refusal-like behavior" — the task-budget page says to start with the p99 of measured per-task spend, the cost guide says "near your loop's 90th-percentile" (the sources differ; the optimizer recommends p99 as the safer start); not supported in Claude Code or Cowork. **[DOCUMENTED: TaskBudget, ContextWin, CostIntel]** — Omit for open-ended quality tasks without a measurable per-task spend. **[DERIVED]**

**R44 — Platform-specific features.** Computer use on the Claude API/Google Cloud only via `{"type":"computer_toolset_20260801"}` (no `name`, no display size; member tools as `tool_use` names; `toolset_name` on every result) — Bedrock still accepts `computer_20251124`. Fast mode (`speed: "fast"`, beta `fast-mode-2026-02-01`, Claude API only, $8/$40; research preview with access on request; switching speed invalidates the prompt cache; not with the Batch API) for latency-sensitive routes, only when the user asks for speed. Batch output up to 300k (beta `output-300k-2026-03-24`). No Priority Tier. **[DOCUMENTED: WhatsNew, ModelPage, Migration, FastMode]**

## Group F — Assumptions from Fable 5 / Opus 5 / 4.x That No Longer Hold

**R45 — "Omitting `effort` means `high`."** True on Fable 5, Opus 5, and earlier Opus models; on Opus 5.5 an omitted effort runs at `medium` — for coding and agentic work about 2.5 SWE-bench-Pro points below `high`. The Opus 4.7/4.8 advice "Start with `xhigh` for coding and agentic use cases" is no longer a default but a measured trade-off (+~1.4 points over `high` at 2.5× the cost) — legitimate when the best result matters most. **[DOCUMENTED: Effort, CostIntel]**

**R46 — "Verifier subagents beat self-critique" / "use subagents frequently" / "delegate more".** Patterns found in older prompts and in the sister Fable 5 optimizer (its R21, sourced there to the Fable 5 prompting guide). On Opus 5 the documented advice is the opposite — it "delegates to subagents more readily than prior models", and "do not use subagents to verify or double-check your own work". Remove, then cap (R22/R23). **[DOCUMENTED: PromptO5] + [DERIVED: transfer]**

**R47 — "Thinking can be switched off" / "omitting `thinking` means no thinking".** True on Opus 4.8 (off when omitted) and Opus 5 (disable at ≤ `high`); on Opus 5.5 every request thinks, so `max_tokens` sized for a no-thinking route truncates replies. **[DOCUMENTED: Migration, WhatsNew]**

**R48 — Manual CoT** ("think step by step", hand-written reasoning plans) was a thinking-off substitute; on Opus 5.5, rely on thinking at a suitable effort; "think carefully" lines in chat system prompts go too (R12). **[DOCUMENTED: BestPract, PromptO55]**

**R49 — Hand-made context/token countdowns in the prompt.** Opus 5.5 receives no context-awareness tags; the documented way to give it a budget is a task budget, which must be sized from measurements (R43). **[DOCUMENTED: ContextWin, TaskBudget]** — Hypothesis: a countdown typed into the prompt text acts like an unmeasured budget and may trigger the failure mode documented for too-small task budgets (decline, aggressive scope-down, early stop). Remove it; if the harness compacts, say so instead (R31). **[DERIVED]**

**R50 — Anti-laziness and thoroughness scaffolding** ("be extremely thorough", "never be lazy", "don't miss anything", "If in doubt, use [tool]"): written to fight undertriggering in older models; documented for the 4.6 generation — "dial back that guidance. Claude 4.6 models are more proactive and may overtrigger on instructions that were needed for previous models", and "If in doubt, use [tool]" "will cause overtriggering" (Opus 4.6). **[DOCUMENTED: BestPract]** + transfer to Opus 5.5, whose Opus-5 predecessor already "verifies its own work without being told to" **[DERIVED]**

**R51 — Aggressive trigger language** ("CRITICAL: You MUST…", all-caps imperatives): documented as an overtriggering cause since Opus 4.5/4.6 — "use more normal prompting like 'Use this tool when...'". **[DOCUMENTED: BestPract]** + transfer to Opus 5.5, which "follows the writing rules you give it" [News] **[DERIVED]**

**R52 — Vague anti-generic design instructions** ("avoid AI slop", "make it look unique", the generic `frontend_aesthetics` sample written for 4.5/4.6): on Opus 5.5 they swap one default style for another; replace with a named-pattern list (R20). **[DOCUMENTED: PromptO55]**

**R53 — Prompt-side vision scaffolding** (step-by-step chart-reading instructions, OCR/table pre-passes, mandatory crop steps written into the prompt): Opus 5.5 reads charts, diagrams, and screenshots "considerably more precisely" without tools — re-test and remove. Keep image tools (container with PIL/OpenCV, or a crop tool) and higher-resolution inputs for the densest material; "Without tools, raising effort improves its reading of technical drawings but does little for charts." **[DOCUMENTED: PromptO55, WhatsNew]**

**R54 — "Text between tool calls arrives as text" / "one fallback model for every refusal".** On Opus 5.5 between-tool notes arrive as `thinking` blocks (R27/R40), and the recommended fallback is category-routed (`fallbacks: "default"`) rather than a pinned Opus 4.8 for all categories; `reasoning_extraction` is never retried. **[DOCUMENTED: WhatsNew, Refusals, PromptO55]**
